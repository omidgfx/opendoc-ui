Deployment

From a single static directory to a hardened Docker stack with an AI gateway — every deployment path, documented end to end.

Static hosting GitHub Pages Docker npm run make Config modes AI gateway Downloader proxy

Static hosting

OpenDoc UI compiles to a single self-contained directory. Build it once, copy dist/ to any static host, and the entire application — documentation, runner, schemas, notes, theming — works without a server process, database or runtime dependency.

Build
npm ci
npm run build      # dist/ with index.html, index.js, 404.html

Deploy dist/ to nginx, Netlify, Vercel, Cloudflare Pages, S3 with a static website, or any Apache server. The included 404.html provides SPA fallback so deep links keep working on hosts without rewrite rules.

GitHub Pages

The repository ships a ready-made Pages workflow. On every push to master it installs dependencies, copies the demo configuration, builds with the correct base path and deploys — so the live demo is always current with the latest commit.

Workflow highlights (.github/workflows/pages.yml)
env:
  VITE_BASE_PATH: /${{ github.event.repository.name }}/
  VITE_LOAD_FROM_URL: 'true'

steps:
  - uses: actions/checkout@v5
  - uses: actions/setup-node@v5
    with: { node-version: 22, cache: npm }
  - run: npm ci
  - run: cp public/demo/config.pages.json public/config.json
  - run: npm run build
  - run: touch dist/.nojekyll
  - uses: actions/configure-pages@v6
  - uses: actions/upload-pages-artifact@v5
    with: { path: ./dist }
  - uses: actions/deploy-pages@v5

Project sites use the /<repository>/ base path automatically; custom domains keep the root. Deep links, the demo specification and local file loading all work unchanged under the subpath because the application routes through the URL hash.

Docker

Docker Desktop or Engine with the Compose plugin is the only prerequisite. The image uses a lockfile-pinned npm ci builder and serves the verified bundle from nginx with a working health check.

Compose
# build and start
docker compose up --build --detach

# open http://localhost:3000 — stop with
docker compose down

docker/config.json is mounted read-only into the container and controls which specifications the deployment presents — edit it and reload the browser; no image rebuild is needed. Host port, image name, container name and restart policy are environment-driven (OPENDOC_PORT, OPENDOC_IMAGE_NAME, OPENDOC_CONTAINER_NAME, OPENDOC_RESTART_POLICY), and helper scripts (docker/build.sh, docker/run.sh and their PowerShell counterparts) cover direct build/run workflows on every platform.

The guided builder — npm run make

For anyone who prefers questions over configuration files, the interactive builder walks through every deployment decision and produces a clean, verified build:

1

Deployment profile

Static files only, a Docker image, or both. Clean the previous output before building if you want a pristine artifact.

2

Frontend options

Apple Emoji sprite (exclude for a leaner bundle, include for consistent Apple rendering), base path, and whether to enable Load-from-URL.

3

Downloader proxy

A validated {URL} template when remote specs must cross restrictive networks, plus optional framework example env files.

4

AI gateway

Provider, model, base URL, hidden API key, auto-generated gateway token, allowed origins, port and limits — with optional framework examples.

5

Docker options

Image and container names, host port (with in-use detection), restart policy.

6

Review, build, start

Confirm the summary, watch the live build, verify the fresh output, then choose to start — preview, dev server, Docker Compose with health polling, or the AI gateway.

npm run make never modifies npm run build. Build-time variables are injected only into the child build process, runtime settings live in .env (secrets never in the gitignored builder.config.json), and the configuration is committed only after the build verifies.

The AI gateway

The assistant can talk to a CORS-enabled provider directly. When that is not acceptable — provider keys must stay server-side, or the network demands a gateway — the repository includes a hardened Express gateway:

Gateway environment (.env)
AI_GATEWAY_TOKEN=replace-with-a-long-random-token
AI_GATEWAY_ORIGIN=https://docs.example.com,http://localhost:3000
AI_GATEWAY_PORT=8787

AI_PROVIDER=openrouter
AI_MODEL=gpt-4o-mini
# AI_API_KEY=   AI_BASE_URL=

AI_GATEWAY_RATE_LIMIT=30
AI_GATEWAY_MAX_CONCURRENT=4
AI_GATEWAY_MAX_MESSAGES=24
AI_GATEWAY_MAX_MESSAGE_CHARS=40000
AI_GATEWAY_MAX_CONTEXT_CHARS=250000
AI_GATEWAY_MAX_OUTPUT_TOKENS=2048
AI_GATEWAY_UPSTREAM_TIMEOUT_MS=60000

Run it with npm run ai-gateway. The frontend proxies /api/ai to it in development, and reference implementations for eight backend frameworks live under ai-proxy/ for teams that want the gateway in their own language and stack.

The downloader proxy

When browsers cannot fetch a remote specification directly — corporate proxies, CORS-restricted hosts — OpenDoc UI can route through a downloader proxy. Configure its template at build time:

Build-time
VITE_LOAD_FROM_URL=true
VITE_SPEC_DOWNLOADER=https://proxy.example.com/download?spec_url={URL}

Reference downloader services for Node, Python, PHP, Go, Java and .NET ship under proxy/, each enforcing origin allowlists, size and timeout limits, redirect caps, port restrictions and rate limiting.
